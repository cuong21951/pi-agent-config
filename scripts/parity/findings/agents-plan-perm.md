# Parity discovery: agents-plan-perm

Area: Agent/Task tool (foreground, background, failure, parallel), plan mode (`/plan`, scrolling), and the permission-prompt system (dialog wording, diff-in-prompt, MCP/web-fetch asks, denial rows, accept-edits auto-apply).

Method: mostly static — Claude 2.1.283's Bun bundle (`~/.local/share/claude/versions/2.1.283`, mmap+regex, `bgrep.py` in scratch) grepped for the literal UI strings, cross-checked against pi's own source (`extensions/claude-modes/*.ts`, `npm/node_modules/@tintinweb/pi-subagents/src/*.ts`, `npm/node_modules/@gotgenes/pi-permission-system/src/*.ts`) including each package's own selftests/docs, which quote what was measured on Claude before. One live side-by-side was run (see "two-parallel-agents" below) via `run.py --scenario parallel-agents --only pi --port 19080` from a copy of `scripts/parity/` in `%TEMP%\pi-parity\discovery\agents-plan-perm\scripts\parity\` (scenario file included there). That run's model resolved to Sonnet 5 via Copilot (not Haiku — `pi_model` was left at the harness default in `run.py` rather than pinned in the scenario file; noted so the cost is visible, no further live runs were made to keep the budget).

## Differences

### Permission dialog: "for this session" grant vs Claude's persistent "don't ask again"
- Claude (evidence): bundle strings (`bgrep.py "don't ask again"`) — `"Yes, and don't ask again for ", pn(x), " commands", "in"/"on", <bold cwd/host>` (bash); `"Yes, and always allow access to ", <bold file>, " from this project"` (Edit/Write — `@227755651`); `"Yes, and don't ask again for ", <bold domain>` (WebFetch — `@229302526`, rule key `domain:${hostname}`); `"Yes, and don't ask again for ", <bold skill>, " in ", <bold dir>` (Skill — `@229298206`); `"...:* commands in ", <bold dir>` (bash-prefix / mcp-shaped rule — `@229298763`). All of these write a rule that persists (to project/user settings), there is no "session" concept in any of them.
- pi now (evidence): `npm/node_modules/@gotgenes/pi-permission-system/src/authority/permission-prompt-component.ts:123-129` — `DEFAULT_SESSION_LABEL = "Yes, for this session"`, `OPTION_LABELS = { y: "Yes", s: "Yes, for this session", b: "Yes, for this session in both directions", n: "No", r: "No, provide reason" }`; `src/presentation/pattern-suggest.ts:118-183` — `"Yes, allow bash \"<pattern>\" for this session"`, `"Yes, allow mcp tool \"<pattern>\" for this session"`, `"Yes, allow skill \"<pattern>\" for this session"`, `"Yes, allow access to external directory \"<pattern>\" for this session"`, `"Yes, allow path \"<pattern>\" for this session"`, `"Yes, allow tool \"<surface>\" for this session"`.
- Difference: pi's always-allow option is phrased and scoped as a **session** grant ("for this session") for every surface (bash, path/edit/write, mcp, skill, external_directory); Claude's is phrased and scoped as a **persistent** grant ("don't ask again" / "always allow ... from this project") that survives past the session, with tool-specific phrasing per surface (bash: "commands in/on X"; file: "always allow access to X from this project"; domain: "for X"; skill: "for X in Y"). This is a wording AND semantic difference, present on every tool type, not just Edit/Write.
- Severity: high (seen on every non-bypass permission ask).
- Feasible in pi: partial — `@gotgenes/pi-permission-system` is an installed package (`npm:@gotgenes/pi-permission-system` in `settings.json`), not one of the patched packages under `patches/`; changing its option labels means either patching it (new `patches/pi-permission-system.patch`, same recipe as the others) or wrapping/overriding the dialog from an extension. Likely owner: `patches/pi-permission-system.patch` (new).
- Test to lock it: a `permission-wording` replay/scenario that triggers an ask on each surface (bash, edit, write, mcp, webfetch, skill) with `bypass:false` and snapshots the option list text for each.

### Permission dialog decline option wording
- Claude (evidence): bundle, `@229154144`/`@229153495` — `"No, and tell Claude what to do differently ", <bold>"(esc)"</bold>`, value `"no"`.
- pi now (evidence): `permission-dialog.ts:65` — `const DENY_OPTION = "No";`, and `permission-prompt-component.ts:127` — `n: "No"`.
- Difference: pi's decline option is a bare "No"; Claude's is "No, and tell Claude what to do differently (esc)" with the `(esc)` hint bolded. Claude has no separate "provide a reason" option in the choice list itself (the reason is typed in a follow-up field after declining, from what the bundle's `r` — "No, provide reason" in pi is pi's own addition, not seen in the Claude strings found).
- Severity: medium.
- Feasible in pi: partial, same owner as above (`pi-permission-system` patch).
- Test to lock it: same `permission-wording` scenario, assert the decline row text.

### Edit/Write permission prompt shows no diff (pi), embeds the tool-use line (Claude)
- Claude (evidence): bundle, `@227857062` — the Edit/Write ask payload is built as `{title: "Read"/"Edit file", subtitle: void 0, question: {kind:"plain", text:"Do you want to proceed?"}, content: {kind:"tool-use-line"}}`. `content.kind:"tool-use-line"` means the dialog's body IS the normal tool-use row — i.e. the same diff rendering already used in the transcript (3-line context, word-level highlight) is what's shown inside the permission prompt.
- pi now (evidence): `npm/node_modules/@gotgenes/pi-permission-system/src/presentation/path-ask-payload.ts` — a path/Edit/Write ask's `PromptPayload.evidence` is built only from `resolvedAliasEvidence` ("resolves to") and `workingDirectoryEvidence` ("working directory"); `prompt-payload.ts` defines `PromptEvidence` as `{label, text, detail}` triples only. `dialog-renderer.ts` renders `evidence` as "one fact per line, `label : value`" — there is no `diff` field or diff-rendering path anywhere in the package (`grep -rn "diff" src` in the package returns zero UI hits).
- Difference: Claude's Edit/Write permission prompt shows the actual diff (the same coloured, word-highlighted diff as the transcript row) as the prompt's content. pi's prompt shows a plain fact table (path, resolved-path alias, working directory) — never the diff itself. A reviewer approving/declining in pi cannot see what changed from the dialog alone.
- Severity: high (this is the core piece of information a human needs to decide, and it is the exact case the brief flagged as unmeasured).
- Feasible in pi: partial — needs the dialog to receive the same diff text/highlight the transcript row already computes (claude-tools' `rows.ts` has the diff renderer) and either add it as a payload evidence entry or splice it into the rendered dialog lines. Likely owner: `pi-permission-system` patch (payload/evidence) + `extensions/claude-tools` (reuse of the diff formatter) or a small glue extension.
- Test to lock it: `permission-editwrite` scenario — trigger an Edit ask on a file with a known diff, snapshot the dialog content, assert it contains the diff lines (not just the file path).

### No generic "User rejected …" transcript row after a decline (only plan-mode has one)
- Claude (evidence): bundle — Edit/Write: `@238745244` → `"User rejected ", <operation>, " to "`, then bold file path (colour `subtle`). NotebookEdit: `@238792662` → `"User rejected ", <edit_mode>, " cell in "`, bold file, `" at cell "`, cell id. These render right under the transcript as the tool's own result row when declined.
- pi now (evidence): `npm/node_modules/@gotgenes/pi-permission-system` has no "User rejected" (or any denial-row) string anywhere (`grep -rn "declined\|rejected\|denied the" src` returns only changelog/doc/config text, never a rendered row); its own `README.md:68` documents the dialog itself (`y/s/b/n/r`) but nothing about what the transcript shows afterward. The one place pi DOES draw a Claude-shaped denial row is plan-mode specifically: `extensions/claude-modes/dialog.ts:172` — `paint("muted", ELBOW) + paint("dim", "User rejected Claude's plan:")`, confirmed byte-identical to Claude's plan-rejection string (`@227357801`).
- Difference: for an ordinary tool ask (Bash/Edit/Write/MCP/WebFetch/Skill) declined outside plan mode, pi has no equivalent "⎿ User rejected X to Y" styled row — only the plan-mode rejection path implements Claude's wording/colour convention.
- Severity: high (denial happens routinely once bypass is off; the transcript currently gives no Claude-shaped record of it).
- Feasible in pi: partial — needs the per-surface wording (from the "don't ask again" finding above) mirrored into a rejection-row renderer keyed by tool kind (bash / edit / write / notebook / mcp / webfetch / skill), analogous to `dialog.ts`'s plan-rejection function. Likely owner: `pi-permission-system` patch (result text) plus a claude-tools row for the "own" tool kinds, or a new small extension.
- Test to lock it: same `permission-wording` scenario, decline an Edit and a Bash ask, assert the resulting transcript row text/colour.

### Two (or more) foreground Agent calls in one turn: Claude groups them, pi does not
- Claude (evidence): bundle, functions `A5r`/`C5r`/`Pm` (`@227561954` onward). When a message's content has more than one Agent/Task `tool_use`, Claude renders ONE combined header — `"<N> background agents launched (↓ manage)"` when all are async, `"<N> agents finished"` / `"<N> <type> agents finished"` when all resolved, or `"Running <N> agents…"` while any are still going — followed by one indented sub-row per agent (component `Pm`, carrying `agentType/description/toolUseCount/tokens/color/isResolved/isError/isAsync/lastToolInfo` per agent). This is a dedicated multi-agent aggregator, distinct from the generic bash/read "collapsed tool group" the README already documents as matched.
- pi now (evidence): live capture, `%TEMP%\pi-parity\discovery\agents-plan-perm\out1\pi-finished.txt` (scenario `parallel-agents.json`, two synchronous `Agent` calls in the same reply) — pi rendered two fully independent, self-contained blocks back to back, each with its own `● Agent(desc) model` header and its own `✓ <stats> · <duration>` / `⎿ Done` (or `⎿ Wrapped up (turn limit)`) line; no combined header, no shared "N agents …" summary line anywhere. Source confirms this is systematic, not a snapshot fluke: `npm/node_modules/@tintinweb/pi-subagents/src/index.ts` `renderCall`/`renderResult` (~line 1689-1780) render per tool-call only; there is no code path anywhere in the package that looks at sibling `Agent` tool_use blocks in the same turn to build a joint header.
- Difference: Claude collapses N simultaneous Agent/Task calls into one "N agents …" line with per-agent sub-rows; pi always shows N full independent blocks. Screen space and at-a-glance status differ significantly as N grows.
- Severity: high for anyone launching >1 agent per turn (increasingly common with multi-agent workflows); this exact case was called out by name in the brief.
- Feasible in pi: partial — needs a turn-level post-process step in `pi-subagents` (or a wrapping extension) that detects >1 Agent tool_use in the same assistant message and renders the Claude-shaped group header + compact sub-rows instead of each call's own full block. Likely owner: `patches/pi-subagents.patch`.
- Test to lock it: the `parallel-agents.json` scenario in this folder (copy into `scripts/parity/scenarios/`), run through `run.py --scenario parallel-agents` both sides, `diff.py` on the "finished" snapshot.

### mock.py cannot exercise Agent parameters beyond description/prompt/subagent_type (harness gap, not a UI bug)
- Evidence: `scripts/parity/mock.py` — `to_claude()`'s `"Agent"` branch only forwards `description`, `prompt`, `subagent_type` (`compact({...})`, no `run_in_background`, `max_turns`, `model`, `resume`, `isolated`, `inherit_context`).
- Consequence: none of `run.py`'s existing scenario machinery can drive Claude's side into background-vs-foreground, max-turns/steered, or model-override states — every such Claude-side capture has to come from `--claude`'s own real API run (as the current `agent.json` scenario does for the background case) rather than the cheap mock replay. Foreground/steered/aborted/error states for Claude specifically were not captured live in this pass because of this; the Claude-side wording for `Pm`'s per-agent sub-row and for a genuine `error`/`aborted` Agent result is inferred from bundle source only, not screen-captured.
- Not a parity difference by itself, but worth fixing so the next pass can actually replay these states: extend `to_claude`'s `"Agent"` branch to forward `run_in_background`, `max_turns`, `model`, `resume`, `isolated`, `inherit_context` verbatim.

### `/plan <description>` has no Claude counterpart
- Claude (evidence): bundle — no `/plan` command string anywhere (`bgrep.py "/plan "` → 0 hits; the mode-name string `"plan"` only ever appears as the internal `permissions.defaultMode`/session-flag value, e.g. `@200980890`'s `UN=["acceptEdits","auto","bypassPermissions","default","dontAsk","plan"]`, never as a slash-menu entry). Claude enters plan mode only via shift+tab mode-cycling or the model's own `enter_plan_mode`/`exit_plan_mode` tool calls (already matched, per README).
- pi now (evidence): README's extensions table lists `claude-modes (... and Claude's plan mode: ... /plan)`; `claude-modes/dialog.ts`'s `rejectedRows`/`approvedRows` even print `"/plan to edit"` as a hint (`ELBOW + "Plan saved to: " + path + " · /plan to edit"`).
- Difference: typing `/plan <description>` in pi does something (opens/continues plan mode with that description as the plan seed); typing the same text at a real Claude Code prompt is not a recognized command at all — Claude would either show "No commands match" in the slash menu (already matched behavior for unknown commands) or, on submit, send `/plan <description>` as a literal chat message to the model. This is a functional divergence pi added on purpose (a convenience shortcut), not a rendering bug — flagging it because the brief asked to check it and because it is not currently recorded anywhere in the README's Matched / Not-matched / Outside-measured lists.
- Severity: low (it's an intentional pi extra, not something a side-by-side transcript diff would flag as wrong looking, but it IS a behavior Claude cannot reproduce).
- Feasible in pi: n/a — this is a deliberate pi feature; "matching" Claude here means removing it, presumably not wanted. Recommend recording it explicitly in README's "Outside the measured set" instead of leaving it silently unlisted.
- Test to lock it: none needed for parity; if kept, a pi-only selftest that `/plan <description>` seeds the plan file's initial content is enough.

### Plan taller than the approval modal: pi hard-truncates, Claude uses a bounded scrollable pane
- Claude (evidence): bundle, `@229256661` — the "Ready to code?" plan body sits inside `e(dE, {ref:Cn?.attach, flexDirection:"column", height:Nn?fn:void 0, stickyScroll:!1, children: ...})`; `dE` is a scrollable-viewport component (same shape as the one used for the main transcript pane) and `stickyScroll:!1` only turns off auto-follow-to-bottom — it does not remove scrolling. The plan markdown itself renders inside a nested `sS` (also a scroll-capable) container. Claude also keeps the already-matched `ctrl+g to edit in <editor>` escape hatch for reading the whole plan outside the TUI.
- pi now (evidence): `extensions/claude-modes/dialog.ts:126-138` (`planDialogRows`) — `const room = Math.max(0, height - head.length - bottom.length - 1); const plan = dialog.planRows.slice(0, room)...`; the selftest at the bottom of the same file states the intended behaviour outright: `"a plan taller than the room is cut so the dashed rule still closes it"` (the `tight` case, 40 plan rows into a 20-row budget). There is no scroll state, no "↓ N more" hint, and no way to see the truncated tail from the dialog itself — only `ctrl+g` (already implemented and matched) gets you the full text.
- Difference: Claude's plan pane can show/scroll to the full plan inside the dialog (bounded height, non-sticky scroll); pi silently drops everything past `room` rows with no on-screen indication that anything was cut.
- Severity: medium (rare in practice since most plans fit; when a plan legitimately is long, pi's tail is unrecoverable from the dialog, only via `ctrl+g`).
- Feasible in pi: partial — would need `planDialogRows` to become scroll-state-aware (track an offset, redraw on arrow/PgUp-PgDn while the dialog has focus) instead of a fixed `slice`. Likely owner: `extensions/claude-modes/dialog.ts` + `index.ts` (would need to wire a new keyboard handler path).
- Test to lock it: extend the existing `plan.json` scenario (or a new `plan-tall.json`) to produce a plan with more lines than the terminal, and assert (once fixed) a scroll affordance appears; until then, the existing `dialog.ts` selftest's `tight` case is the pinned "this is what pi does today" record.

## Summary (10 lines)

- High: 4 — permission "for this session" vs persistent wording (all surfaces), Edit/Write prompt missing the diff, no generic denial transcript row, two-parallel-agents not grouped.
- Medium: 2 — decline option wording ("No" vs "No, and tell Claude what to do differently (esc)"), plan-taller-than-modal hard truncation vs scroll.
- Low: 1 — `/plan <description>` has no Claude counterpart (intentional pi feature, not a bug).
- Not applicable: 1 — `SubagentWorkflow` (pi-only tool, no Claude equivalent).
- Harness gap (not a UI finding): `mock.py`'s Agent-tool mapping drops `run_in_background`/`max_turns`/`model`/etc., blocking cheap replay of background/steered/error/model-override states.
- Top 5 by impact: (1) permission dialog wording is session-scoped everywhere instead of Claude's persistent "don't ask again" phrasing; (2) Edit/Write permission prompt never shows the diff Claude embeds in it; (3) two-or-more foreground Agent calls render as separate blocks instead of Claude's grouped "N agents …" header; (4) no transcript row at all for a declined non-plan tool ask; (5) a plan longer than the terminal is silently cut in pi with no scroll/indicator, vs Claude's bounded scrollable pane.
- Matched and reverified: shift+tab feedback hint text, plan-mode "User rejected Claude's plan:", `ctrl+g` edit-in-editor hint, accept-edits auto-apply gating, background-agent fleet-list lifecycle.
