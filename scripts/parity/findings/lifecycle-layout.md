Measured against Claude Code 2.1.283 (`C:\Users\cuong\.local\share\claude\versions\2.1.283`, decompiled with mmap+regex, UTF-8/UTF-16LE) and pi (`%LOCALAPPDATA%\Volta\...\pi-coding-agent\dist\bundle\cli.js` + `C:\Users\cuong\.pi\agent` extensions/patches), Cuong's harness. Live captures used the parity mock (`scripts/parity/mock.py`, port 19060-19065 from my assigned range 19060-19079) or direct `--session` replay (no model at all). Scratch files under `%TEMP%\pi-parity\discovery\lifecycle-layout\`. Test Claude transcripts and their `~/.claude/projects/...` folders were deleted after capture.

### Context-low warning and auto-compact notice — pi has none of it
- Claude (evidence): bundle strings at `0xda37c00` (function `Q1`): a context-indicator row that is `null` (nothing drawn) while usage is classified "ok", then shows dim `wrap:"truncate"` text `${N}% until auto-compact` (or `${100-N}% context used` when the window is unenforced), escalating to `color:"error"` text `Context low (${N}% remaining) · Run /compact to compact & continue` (omits the `/compact` suggestion when `DISABLE_COMPACT` is set, or appends a custom hint instead). Also found: mid-compaction spinner text `"Compacting conversation…"` (bundle `0xcf51450`/`0xd942a22`), and a post-compaction transcript marker `"Conversation compacted (${ctrl+o} for history)"` (bundle `0xd9ecbf3`), dim, 8s timeout. Live capture `claude-190k.txt`/`claude-199k.txt` (mock `--context-tokens 190000`/`199000`) confirms the row renders right-aligned, dim, directly above the flat rule/prompt box, independent of and differently-worded from Cuong's own `[PONYTAIL] · ... · ctx N%` footer badge (which sits one row further down and is computed differently: `ctx 95%` vs `0% until auto-compact` for the same 190k/200k tokens). Could not get the red "Context low" variant to trigger with fabricated `--context-tokens` on a 1-turn conversation (likely gated on real compactable history, not just reported usage) — reported from bundle source, not from an on-screen capture.
- pi now (evidence): `grep -c compact` on pi's entire bundled `cli.js` = 0 (zero matches, checked with the literal word "compact"). `grep -rn compact extensions/ --include=*.ts` (excluding `claude-footer`'s own `ctx N%` percentage math) finds only a decorative `/compact` entry in `claude-slash-menu`'s menu list — no handler, no indicator, no compaction logic anywhere in the harness.
- Difference: pi shows nothing as context fills up beyond its own footer's `ctx N%` badge (already an accepted, differently-styled substitute per README). It never shows the passive "N% until auto-compact" countdown row, never escalates to a red low-context warning with a `/compact` call to action, never shows a "Compacting conversation…" state, and there is no `/compact` command to run even if a user tried (pi has no compaction feature at all).
- Severity: high (every long session eventually needs this; currently pi gives no in-band warning before running out of context).
- Feasible in pi: partial — the visual row is easy to add to an extension (mirrors the existing `claude-footer` ctx-percent math), but real auto-compaction is a pi-core feature gap, not just a rendering gap; likely owner: new extension for the indicator row (e.g. `claude-footer` or a sibling), pi-core patch (or accepted "Not matched" ledger entry) for actual compaction.
- Test to lock it: a replay fixture that calls mock.py with `--context-tokens` near/over the model's window and asserts the dim/red row text and colour; a second fixture asserting the "Compacting conversation…" spinner text and post-compact marker once pi has any compaction support to test against.

### Resuming a session: startup notice placement differs
- Claude (evidence): `claude-resumed.txt` (2.1.283, `claude.exe --resume <copy-of-a-real-transcript>`) and the pre-existing `%TEMP%\pi-parity\resume\resumed.txt` (2.1.280, different day/version) both show the SAME shape: `[header] → [agents-md notice, part of the replayed history] → [replayed transcript] → [agents-md notice AGAIN, fresh for this launch] → [prompt box]`. The `"● agents-md: no CLAUDE.md found; AGENTS.md loaded: ..."` line (dim `999999`) appears twice — once where it was originally recorded, once appended right after the last `done` line of the redrawn history, immediately before the live prompt.
- pi now (evidence): `pi-resumed.txt` (replaying `replays/task.jsonl` via `--session <copy>`, no model) shows `[header] → [Ponytail loaded: full] → [replayed transcript] → [prompt box]` — the notice appears ONLY ONCE, at the very top, and is never repeated after the redrawn history. `patches/README.md:41` documents the intent ("ponytail prints `Ponytail loaded: <mode>` on every session start... and resume"), but the fresh-launch notice lands in the pre-history slot, not the post-history slot Claude uses.
- Difference: Claude's fresh per-launch startup notice is the LAST thing before the prompt (closest to where the user's eye already is, right under the just-replayed history); pi's fresh per-launch notice is the FIRST thing after the header (above the entire replayed history, easy to miss if the history is long).
- Severity: medium (visible on literally every resume, but cosmetic/ordering only).
- Feasible in pi: yes; likely owner: `patches/ponytail.selftest.ts` / whatever patch emits the "Ponytail loaded" notify call — move the emission to fire after the historical redraw completes instead of at process boot.
- Test to lock it: extend `replays/task.jsonl`-style fixture to a `--session` replay assertion that the notice's row index is `> ` the last historical `done` line's row index.

### Exit summary text and mechanism
- Claude (evidence): bundle `0x62b29dd`/`0xc64e0f7`: `pe.dim("\nResume this session with:\nclaude ${worktree}--resume ${id}\n")`. Live double-Ctrl-C capture `claude-exit2.txt` rows 38-39 confirm the literal two-line text `Resume this session with:` / `claude --resume <uuid>` prints after the TUI tears down (the old alt-screen's `❯`/rule glyphs are left over from the previous frame, not part of the message). Bundle also has `"Press Ctrl-C again to exit"` / `"(press Ctrl+C again to exit, or Ctrl+D)"` and a changelog line confirming it now takes exactly 2 presses (down from 3-4 while a background agent runs).
- pi now (evidence): live double-Ctrl-C capture `pi-exit-pi-afterexit.txt` rows 79-80: `To resume this session: pi --session-dir '<full quoted dir>' --session <uuid>`, wrapped onto 2 physical rows because of the extra `--session-dir '<dir>'` clause; colour dump shows only the label `To resume this session:` is dim, the command itself is default/undimmed (Claude dims the whole two-line block per `pe.dim`). Also: pi's FIRST Ctrl+C did not show any "press again" warning at all — it flipped the mode row to `⏸ manual mode on` instead (a real state change, not a confirmation prompt); the SECOND Ctrl+C then exited. `grep -c "ctrl+c"` / `"again to exit"` / `"Resume this session"` on pi's bundle and on `extensions/**/*.ts` = 0 matches everywhere.
- Difference: (1) wording — "Resume this session with:" vs "To resume this session:"; (2) command shape — bare `claude --resume <id>` vs `pi --session-dir '<dir>' --session <id>` (longer, always repeats the directory, wraps at normal widths); (3) colour — whole block dim (Claude) vs only the label dim (pi); (4) mechanism — Claude's first Ctrl+C is a no-op except for a temporary "press again" hint; pi's first Ctrl+C actually changes mode to manual, a visible behavioural side effect Claude doesn't have.
- Severity: high (the exit text is the very last thing on screen every session, and the Ctrl+C semantics difference could surprise a user expecting Claude's warn-then-exit).
- Feasible in pi: yes; likely owner: whatever prints the "To resume this session" line (pi core, not found in `extensions/`) — could shorten to omit `--session-dir` when it equals pi's own default session dir; the Ctrl+C-vs-manual-mode behaviour is pi core's key handling, needs a pi-core patch to add a genuine "press again to exit" confirmation state instead of switching modes.
- Test to lock it: a `pty-capture.py --steps` scenario sending `\u0003` twice at idle and asserting on the exact two exit-message lines' text/colour and on there being no mode-row change from the first press.

### Short terminal (24 rows) and very long transcript scrolling: pi keeps real scrollback, Claude does not
- Claude (evidence): `run.py --replay replays/markdown.jsonl --rows 24/45 --cols 80/60` (mock-backed, no live cost): the pyte `HistoryScreen.history.top` (real terminal scrollback pi-capture reconstructs) is empty in every capture (`claude-resize-*.txt`: `history_nonblank=0` at 100, 60, and 100-again cols; `narrow80b/claude.txt` at 24 rows: dump is exactly `a.rows` (24) lines total, and it visibly starts mid-table, i.e. the top of the transcript — header, the `agents-md` notice, the prompt line, the heading, the first paragraph — is simply gone, not scrollable back to).
- pi now (evidence): the same fixture through pi (`pi-mdresize-*.txt`, `narrow80b/pi.txt`) always has a non-empty `history.top` (6 lines at 40 rows/100→60→100 cols; total dump 51-52 lines at 24-45 row viewports) — the header/logo/"Ponytail loaded" rows that scrolled off the top are still sitting in real terminal scrollback and reappear in the dump.
- Difference: Claude Code manages its transcript entirely inside its own viewport (an Ink alt-screen-style full clear+redraw), so content that doesn't fit is truly gone from the terminal's native scrollback — a user cannot mouse-wheel or `tmux copy-mode` up to see turns that scrolled past the top. pi lets old rows scroll into the terminal's real scrollback via ordinary linefeeds, so they remain recoverable there.
- Severity: high (affects every session once the transcript exceeds the terminal height, which is common; also directly explains why a short 24-row terminal behaves very differently under the two harnesses).
- Feasible in pi: partial — matching Claude exactly would mean pi stops relying on real scrollback for anything above the live viewport, which is a rendering-architecture change; likely owner: pi-core patch (`patches/pi-coding-agent.patch.mjs`) around however the transcript region is drawn, not a small extension fix. Note this may be a deliberate, already-accepted difference (README "Scrollback is left alone for same-height repaints" suggests it was a conscious choice) — flag for Cuong to decide if it should be closed or added to the ledger as an accepted exception.
- Test to lock it: `pty-capture.py --rows 24` on a fixture whose total rendered height is known to exceed 24, then assert `screen.history.top` length is 0 for Claude and > 0 for pi (already effectively what `narrow80b` demonstrates); wire into `diff.py` as a named exception either way.

### Narrow terminal (60 cols): footer/mode-row truncation style differs; paragraph/table/code wrap already matches
- Claude (evidence): `narrow60/claude.json` row 43 (footer): `'  [PONYTAIL] · Haiku 4.5 · ctx 0% · Fable ██████████ 0% ↻…'` — hard character-level cut with a trailing `…` (Ink `wrap:"truncate"`), same on the mode row: `'  ⏵⏵ bypass permissions on (shift+tab to cycle) · ← 7 age…'`.
- pi now (evidence): `narrow60/pi.json`: `'  [PONYTAIL] · Haiku 4.5 · ctx 0% · deepseek $11.61'` (the trailing `· openrouter $16.37` segment is dropped whole, no `…`) and `'  ⏵⏵ bypass permissions on (shift+tab to cycle)'` (the `· ← 7 agents` clause dropped whole, no `…`). Note pi's OWN header subtitle line does use an ellipsis elsewhere (`Claude Haiku 4.5 (latest) with high effort · ...`, literal three ASCII dots) — so pi has ellipsis-style truncation somewhere, just not applied to the footer/mode row.
- Also checked and MATCHES: at 60 cols (tall viewport, no scrollback confound) the wrapped paragraph, nested/ordered lists, GFM table box, fenced code, and blockquote from `replays/markdown.jsonl` render byte-identical between pi and Claude (`narrow60/pi.txt` vs `narrow60/claude.txt`, lines 5-38 of each) — the wrap-ansi parity already documented in the README ledger holds down to 60 columns, not just 132.
- Difference: Claude truncates the footer/mode row character-by-character with a unicode `…`; pi truncates by dropping whole trailing clauses with no marker at all.
- Severity: low (only matters below ~70-80 columns, and both are readable, just styled differently).
- Feasible in pi: yes; likely owner: `extensions/claude-footer/index.ts` (compose the badge with a length budget + `…` fallback instead of the current segment-drop logic).
- Test to lock it: extend `extensions/claude-footer/index.ts`'s existing self-test with a narrow-width case asserting a trailing `…` when the composed line would exceed the given width.

### Unicode/CJK/Vietnamese wrap matches; a flag-emoji width edge case does not (different bugs on each side)
- Claude (evidence): `unicode-out/claude.txt` (mock-backed, prompt "Show the unicode sample.", content = Vietnamese diacritics + CJK + emoji + a GFM table, 100 cols): Vietnamese paragraph wraps at the exact same point as pi (rows 12-14 identical); CJK paragraph wraps at the exact same point as pi (rows 16-17 identical). The emoji line renders `🚀 🎉 👍 🇻🇳spaced among ascii words to check column width 🙂 and combining marks like` then wraps whole — but the space between `🇻🇳` and `spaced` from the source text is silently swallowed (`🇻🇳 spaced` → `🇻🇳spaced`), i.e. Claude's width table undercounts the flag-emoji by one column.
- pi now (evidence): `pi-unicode3.txt` (same session content replayed via `--session`, no model, 100 cols): the space after `🇻🇳` is preserved correctly (`🇻🇳 spaced`), but the wrap breaks the following word itself: `...combining marks li` / `ke` — pi's wrapper splits "like" into "li"+"ke" across two lines, a genuine word-wrap violation (Claude never breaks mid-word anywhere in either capture).
- Also: the markdown table's CJK header cell pads differently — Claude shows `│    语言    │` (extra leading padding, reads as roughly centered) while pi shows `│ 语言       │` (flush left, only trailing padding) for the same default (unaligned, i.e. GFM-default-left) column — likely both sides computing the CJK double-width column budget slightly differently; not scored as a bug either way, just noted as a visible difference.
- Difference: both engines mis-measure the same flag-emoji sequence, but in different ways — Claude eats an adjacent space (cosmetic), pi breaks a word in half (a real word-wrap correctness bug, more visible/severe than Claude's glitch).
- Severity: medium (flag emoji specifically; plain Vietnamese and CJK text wrap correctly and identically on both sides, which is the common case).
- Feasible in pi: yes; likely owner: whatever width table backs pi's line-wrapping (probably a shared string-width helper under `extensions/` or a patched package) — needs to treat the flag sequence as one atomic grapheme so a following space/word can't get glued to the previous line's tail after it.
- Test to lock it: a fixture with `🇻🇳` (or another regional-indicator flag) immediately followed by a long word near a wrap boundary, asserting no mid-word break and that surrounding spaces survive; good candidate for `replays/wrap.jsonl` or a new `unicode.jsonl` (spec used for this measurement can be found at `%TEMP%\pi-parity\discovery\lifecycle-layout\spec-unicode3.json` / `unicode3.jsonl`).

### Light theme, colour-blind themes, ANSI-only themes, and NO_COLOR: pi has none of them
- Claude (evidence): bundle `0xbf829eb`: theme enum `["dark","light","light-daltonized","dark-daltonized","light-ansi","dark-ansi"]` (plus `"auto"` = match terminal), with menu labels `"Dark mode"`, `"Light mode"`, `"Dark mode (colorblind-friendly)"`, `"Light mode (colorblind-friendly)"`, `"Dark mode (ANSI colors only)"`, `"Light mode (ANSI colors only)"` (bundle `0xdfd0cf6`+). Separately, `NO_COLOR` is read and respected (bundle `0x56927a9`+: warns when both `NO_COLOR` and `FORCE_COLOR` are set, and disables colour/hyperlinks per `NO_COLOR=1` per its own man-page text at `0x50c85cd`/`0x50d1616`).
- pi now (evidence): `C:\Users\cuong\.pi\agent\themes\` contains exactly one real theme file, `claude-dark.json` (plus `.bak-*` history files that are not loadable themes) — no light variant exists to load even via `--use-theme`. `grep -c NO_COLOR` on pi's entire bundled `cli.js` = 0; `grep -rniE "no_color|light.?theme" extensions/` = 0 matches anywhere in the harness.
- Difference: pi cannot render light mode, either colour-blind-friendly variant, either ANSI-16-only variant, or auto-detect from the terminal's background — only the one hand-built dark theme exists. pi also does not honour `NO_COLOR` at all (untested whether colours still print with `NO_COLOR=1` set, but there is no code path that could suppress them, so they almost certainly do).
- Severity: high for anyone on a light terminal/colour-blind, but low for Cuong's own daily usage (always dark) — flagging as a real gap rather than a P0.
- Feasible in pi: yes for a light theme (author a `claude-dark.json`-shaped `themes/claude-light.json` with light-appropriate `vars`/`colors`, matching Claude's light palette by capturing it via `--use-theme light` — not done here); NO_COLOR support needs a pi-core check (`process.env.NO_COLOR`) gating ANSI emission, likely a pi-core patch since no extension controls global colour output.
- Test to lock it: `pty-capture.py --env NO_COLOR=1` on a simple scenario, asserting zero SGR codes in the raw output for Claude and (currently, expected-fail) for pi; a `--use-theme claude-light` capture compared against a live `claude --settings '{"theme":"light"}'` capture once a light theme file exists.
